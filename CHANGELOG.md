# Changelog

All notable changes to Eling are documented here. Follows [Keep a Changelog](https://keepachangelog.com/) and [Conventional Commits](https://www.conventionalcommits.org/).

## [Unreleased] - 2026-11-18

### Changed
- **Convention tests enforce their rules with zero exceptions (tests + backend + desktop)**: the four grandfather allowlists are gone — `SilentCatchAllowlist` (~177 baseline sites, swept and removed file by file; every catch block now logs), `TupleAllowlist` (12 files converted to named records, incl. `SqliteMemoryIndex`'s FTS rank rows, `RuntimeRegistry`'s alive-service pairs, `FileSystemService`'s newline-normalize/line-slice results), `ProcessStartInfoAllowlist` (long-lived backend spawn and the test process fixture now go through CliWrap — FrontendDevSpawner's netstat probe included — with stdin handled by a small blocking `TestStdinStream` for the MCP handshake), and the already-empty `MultiTypeAllowlist` machinery (`NoNew/NoStale` companion tests deleted). `NoTuples_BeyondAllowlist` is now `NoTuples`, and `CatchBlocks_MustNotBeSilent` is a plain zero-exception scan. Nothing may be grandfathered in: a compliant site is a real fix. NuGet: desktop gains `CliWrap` 3.10.5 (same version the backend uses).
- **Full-suite flakes fixed (tests + core)**: `CodebaseWorktreeInheritanceTests` moved into `ElingDataDirCollection` (was `WorktreeIndexCollection`, parallel) — it flipped process-wide `ELING_DATA_DIR`, which the self-contained test hosts' live `ElingPaths.ResolveDataDir` picked up mid-run and retargeted their skill index under them (adopt POSTs 404'd under load). `RuntimeRegistryWorkspacePruneTests` now polls the catalogue instead of asserting after a single prune call, which the registry's fire-and-forget startup prune can silently decline to overlap. Three full `api` runs green.
- **`JsonWorkspaceRegistry` gate is now per-file instead of one machine-global `Global\eling-workspaces-registry` mutex (core)**: the global gate serialized every registry in every process on the machine, and exceeding the 5s budget dropped the registry write silently (the caller's catch swallowed the timeout — full-suite hosts en masse could starve it). The per-file gate (SHA-256 of the full path) serializes exactly the writers that touch one file, which is all the correctness needs.

- **Commit lease is now mandatory in the MCP server instructions (backend + MCP)**: the `Commit lease` section opens with `MANDATORY - no exceptions` and explicitly forbids `git commit` (and any git-index/history operation) without a first `commit_lease` that returned `verdict: 'green'` / `acquired: true`. No exception is allowed for small, docs-only, or single-file commits - the hazard is the shared index, not the file count. Agents now re-claim the lease immediately before `git commit` to refresh its heartbeat (the only renewal available while no heartbeat tool exists), and pass `ttl_seconds: 1800` when the pre-commit hook runs a slow suite. The verdict contract, `commit_wait`, `commit_release`, `lease_token`, `intent_mismatch`, and the shared-index rules are preserved; `MemoryToolsTests` locks the new wording.

### Added
- **`pnpm dev:supervised` — a watchdog for the dev loop (scripts)**: `dotnet watch` restarts the backend only when a file changes, so a backend that crashes on its own, or a watch whose build loop dies on a locked file, stays down until the next edit. `scripts/dev-supervisor.ps1` sits one hop above it: it starts `dotnet watch` with the same project and environment the `eling_dev` MCP entry uses, probes `GET /health` every 5s, and compares the answering `pid` against the child tree so a foreign process holding 4417 never counts as healthy. Twelve silent probes (60s — a rebuild takes ~25-30s and the app answers nothing during it) kill the tree and restart it; a child that exits on its own restarts after backoff (2s doubling to 30s, reset after 2 minutes of uptime). One supervisor per machine via a named mutex, every decision appended to `.bin-opencode/dev-supervisor.log`. It is a watchdog, not a bridge: a restart replaces the process holding the MCP stdio pipe, so an MCP client attached to it reconnects on its own schedule. The child's stdin is redirected and never closed — without that the backend's stdio MCP transport sees EOF and shuts the app down ~1s after starting whenever the supervisor runs from a non-interactive parent.
- **MCP server instructions now tell every agent about skills - check, follow, offer to create or update (backend + MCP)**: a new `Skills (workflows)` section in the initialize handshake text clients receive. Agents are told to check `skill_search` (or the `skills` block in `recall`) before a multi-step workflow, to read and follow a matching SKILL.md step by step without skipping, reordering, or improvising (stop and ask when a step fails or does not fit), to flag up front when no skill matches and the workflow looks repeatable, to propose a drafted skill once the work is done (proposal-first, never silently, `skill_save` only after the user approves), and to propose updating an existing skill when the user's durable corrections rewrite its steps - whether stated before the work starts or after, and likewise when a skill is noticed stale by reading; a correction that is only a rule stays a memory - the skill is not rewritten for it. If during execution the workflow diverges from the skill (skipping, reordering, or doing a step another way - including a different route the user asks for on this run), the agent must stop and ask whether the skill should be updated or left as it is - the change may be only temporary - never silently drifting from the skill. Closes the gap where Smart Create was documented in the skill-management spec as agent behavior but never reached the instructions clients actually read - a session with a matching skill could still improvise and skip steps. Proposal-first on every write path; no backend detection, no recall payload change.
- **Server-instruction skill trigger now fires on bare commands and respects scope (backend \+ MCP, follow-on to the 2026-11-18 entry)**: the `Skills (workflows)` section previously triggered only "when the user asks for a multi-step workflow", so a one-word command (`commit`, `push`, `deploy`) never opened the skill check - the agent had `recall`'s obligation to remember and no obligation to load the procedure. Now: every incoming request is a potential trigger, including one-word commands, and the check runs BEFORE responding/acting - first the `skills` block `recall` returned (when present), else `skill_search`. A **scope-fit rule** is added: a hit is loaded only when its *description's* stated scope (repo family, stack, workspace) contains the current workspace; the scoping signal is the description, never the name; when several fit, load the most specific. The `Recall` section gains one clause treating the `skills` block as a load queue. No tool, pipeline, or payload change; `MemoryToolsTests` extended with assertions locking the trigger + scope-fit language in place.

### Fixed
- **Elasticsearch auth errors (core + backend + MCP)**: a cluster 403 is no longer reported as "authentication failed (401): the cluster requires credentials". The ES status is now carried on `ElasticsearchUnauthenticatedException` and caller-safe messages distinguish missing credentials (401) from a missing privilege (403) without echoing the account name; REST responses, the `es_*` MCP tools and the audit verb all use the real status.

### Fixed
- **SQLite would have served wrong numbers for every non-tinyint numeric filter (core)**: `Microsoft.Data.Sqlite` binds `decimal` parameters as TEXT, and SQL text compares greater than any real number — numeric filters on SQLite silently returned zero or all rows. Decimals now bind as REAL/double.
- **The Data tab's Apply could silently drop the header's sort (dashboard)**: the panel's sort rows were a mount-time snapshot of the tab's sort, and Apply overwrote the tab with it, undoing whatever the grid header had since committed. Panel sort rows now render straight from the committed sort until the reader edits them in the panel.
- **`/browse` validates disabled rows not at all** (a stale disabled row pointing at a since-dropped column no longer 400s the Apply), carries the table name into the audit trail's `db.browse` entries when a WHERE exists, clamps `page`/`limit` instead of refusing them, runs a SqlSafety read-only tripwire on the built statement, reports `truncated`, and accepts SQLite's `POINT`-type columns. `QueryCacheKey` is injective by construction (length-prefixed segments), so two filter values can never answer for each other's rows.

### Added
- **`commit_lease` now folds the conflict check into the claim - one atomic gate, `commit_check_conflict` is gone (breaking for MCP clients, core + backend + MCP)**: Agents always called `commit_check_conflict` and then `commit_lease` back to back; the preflight fold makes it a single atomic gate instead of a two-step with a race window between the check and the claim. ### Changed

### Fixed

- **`ToolExceptionFilter` logs `InvalidProjectTargetException` as a warning (backend + MCP)**: an unknown ancestor-scope request is expected caller-input validation, not a server fault; the filter now logs a short warning (no stack trace) for it, and genuine faults keep the error-with-stack-trace path.

## [Unreleased] - 2026-11-05

### Fixed
- **The log's `[project:]` field names the opened workspace, not the scope root (backend)**: the identity came from the scope chain's head, so opening `<repo>/service` under a scope at `<repo>` logged `repo` - and two services under one scope logged as the same project, though they write memories to different places and are different projects to the reader. `ProjectId.FromWorkspace` now takes the name of the folder the host opened; the scope root stays visible where it belongs, in the runtime registration's `HeadScopeRoot`. The HTTP host resolves its identity the same way, so the two containers no longer disagree about which project a line belongs to.
- **A malformed appsettings.json in the workspace no longer stops the MCP server from starting (backend)**: the MCP host is launched in the user's workspace, and the .NET generic host takes its content root from there - so `Host.CreateDefaultBuilder()` loaded the workspace's own `appsettings.json` and `appsettings.{Environment}.json` as host configuration. A file that was not valid JSON (an unclosed brace, an unquoted key, single quotes, an empty file) made `builder.Build()` throw `InvalidDataException` - `Could not parse the JSON file` - and the exception escaped `Program.Main`, so the server never started and every tool call failed. Eling reads no configuration key at all, so those files contributed nothing it needed. The MCP host now clears the configuration sources and keeps environment variables, the same isolation the HTTP host already applied.
- **`db_detect_connections` reads the workspace the host opened, not the process working directory (backend)**: `AppSettingsSourceResolver.Resolve` falls back to `Environment.CurrentDirectory` when it is not told the workspace, and that fallback outranks the host content root - so the connection scanner depended on a process-global value that only happened to be the workspace. - **Chat tool `tools_policy`**: List, enable, disable, and reset for individual tools or whole groups from chat, with protected tools rejected and every mutation persisted through the store.

### Changed
- **Recall overflow summarized, not skipped (`recallSummary`)**: `recallLimit` used to end the story — the search asked for at most N hits, so relevant items ranked N+1 and beyond never left the FTS layer. The recall service now takes a second, wider fetch (only when the cap is actually filled, so the interleave guarantee for the top N is unchanged), and the hits beyond the limit are summarized into a new `recallSummary` response field: `{ itemCount, summarizedCount, source, paragraphs[] }` — multi-paragraph by design, so a long record is split across paragraphs instead of crammed into one. The digest is written by the semantic judge when configured (`ProviderSemanticJudge` now also implements a new `ISemanticSummarizer`, sharing the same per-user config store, Polly pipeline, and circuit breaker; `RecallSummaryPrompt` is the pure, unit-tested prompt) and degrades to a deterministic digest (`RecallSummaryFallback`, bounded at ten items / five paragraphs / ~180 chars per fragment) when the judge is unconfigured, times out, fails, or returns nothing usable — with the cause recorded in `note`, mirroring the save pipeline's `judge-failed: ...; fell back` posture. `source` tells the two apart (`judge` vs `heuristic`); `summarizeOverflow: false` skips the summary for minimum latency. The MCP instructions, both tool descriptions/schemas, `docs/recall-architecture.md` §6, and `docs/semantic-judge-architecture.md` §6 document the contract.
- **Standing baseline in every `memory_recall` response**: Recall no longer depends on the caller choosing good topics to stay consistent. Every response now carries `standingMemories` — a topic-independent baseline of active standing rules/preferences, standing decisions, and lessons, ordered current-project first then most recently updated, capped at five, with ids already present in the topic hits excluded. It is derived from the same active-memory enumeration that already fed `recentMemories`, so there is no extra query. Entries are marked `matchedVia: ["standing"]` / `queryMode: "standing-baseline"` so clients can tell them from search hits. The MCP server instructions, the tool description, and `docs/recall-architecture.md` describe it as the server-enforced consistency spine: a narrow topic call still surfaces the standing spine.
- **Session-start recall is broad by design**: The MCP server instructions, the `memory_recall` tool description, the builtin-agent wrapper (`MemoryRecallAgentTool` description + JSON schema), and the in-app agent system prompt (`AgentTurnService`) now mandate a BROAD first-turn topic set — the opening message's topics plus standing rules and preferences, standing decisions, lessons and known gotchas, workflow/repo conventions, and recently touched work — instead of anchoring solely on the opening message's subject. The instruction text shows the exact call shape (`context: { topics: [...] }`, with the top-level `topics` alias noted) and requires a `stats.recallCount` self-check after the call: zero means mis-shaped or no match, so re-issue before treating recall as done (bounded retries). `docs/recall-architecture.md` corrects its call-shape example — which had shown the flat shape that silently failed — and gains two strategic rules: session-start breadth and the zero-result self-check.

The file viewer docks as a right-hand column at xl+ with the list column fixed and the viewer filling the rest; below xl the centered modal remains. - **Workspace catalogue self-cleans rows whose folder is gone**: `JsonWorkspaceRegistry` treated every row as permanent — once a folder was registered, its `agent-workspaces.json` row outlived not just the process that wrote it but the folder itself, so a deleted project or a cleaned-up temp dir left a listing entry pointing at nothing forever (observed live: 12 of 39 rows in the real catalogue pointed at missing folders — 9 `eling-lifecycle-*` and 3 `eling-smoke-*`, all test leftovers). `IWorkspacesRegistry.DeleteMissingRootsAsync` drops rows whose workspace folder no longer exists on disk and reports how many were removed, under the same cross-process mutex gate as every other mutation, rewriting the file only when something was actually dropped, and never throwing — a failed prune costs a few dead rows until the next pass. `RuntimeRegistry.Sweep` invokes it after every sweep (default 15s), outside the runtime lock — the store serializes its own file access, so holding the lock across file IO would only stall every other caller — with an interlocked overlap guard so a slow prune is never piled on by the next tick, and an information log recording how many rows a pass removed. Rows whose folder still exists are kept even when their process is dead, which is the catalogue's whole point (a codebase index stays readable after its owner exits); the sweep comment that used to say "nothing is written to the catalogue here" now distinguishes the two cases: a dead process keeps its row, a dead folder loses it.

- **`memory_save` default scope flips to `project-local`** (user decision 2026-10-14): `MemoryScopePolicy` (blank + the `auto` alias), the `memory_save` MCP tool, and the builtin-agent wrapper all default to `project-local` (machine-only, never committed) instead of `project`. The `ServerInstructions` scope rules, both tool descriptions/schemas, and `docs/using-eling.md` encode the same order: `global` for knowledge that holds in a different, unrelated project; `project-local` for anything bound to this repo; `project` (committed, shared via git) only on explicit request.
