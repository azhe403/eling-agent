# Changelog

All notable changes to Eling are documented here. Follows [Keep a Changelog](https://keepachangelog.com/) and [Conventional Commits](https://www.conventionalcommits.org/).

## [Unreleased] - 2026-10-16

### Added
- **Workspaces page marks the dashboard-port owner**: each workspace card now shows an `owner · :{port}` badge when one of its processes owns the dashboard HTTP port — `4317` global/staging, `4417` dev (`ELING_DASHBOARD_PORT`) — resolved live via `DashboardPort.Resolve()`, so no card needs expanding to see who holds the port. Backend exposes `DashboardPort` on `RuntimeInfoDto` (set only for the owner row); frontend aggregates it to `ownerPort` per workspace group.

### Changed
- **Pre-commit one-layer-per-commit has no bypass**: the `ALLOW_MIXED=1` escape hatch is removed — mixed-layer commits now always fail with the split instruction. `SKIP_HOOK=1` / `--no-verify` remain for test-bypass emergencies only.

### Added
- **Audit Trail Phase 1 — core engine**: The engine half of the audit-trail system (design `docs/superpowers/specs/2026-09-11-audit-trail-design.md`, amendments A/B/C; plan `docs/superpowers/plans/2026-09-11-audit-trail-phase1-core-engine.md`, amendment A7) landed under `Eling.Core.Audit` with no production hooks (those are Phases 2-5). Machine-global store root resolves through `ElingPaths.ResolveAuditDir` + `CentralAuditDirectory` beside `logs/`. Entry schema: one JSON line per event (`AuditEvent`/`AuditMetadata`) via source-generated `AuditJsonContext` — camelCase fields, null omission, string enums with canonical kebab-case labels (`change`/`access`, `memory`/`runtime`/`filesystem`, `project`/`project-local`/`global`, `success`/`error`/`denied`) through policy-carrying converters registered at the context level. Ambient actor propagation (`AuditActorContext`, AsyncLocal) with the `unknown` default. Storage: `AuditFileStore` appends per-trail per-day JSONL through an exclusive handle (`FileShare.Read` + bounded retry for cross-process, an in-process semaphore for same-process writers), lazy daily rotation to `.jsonl.gz` with an injected clock (no timer), a rebuildable normalized SQLite read cache (`audit_events`/`audit_state`/`audit_tags`, no JSON payload column, WAL + busy_timeout pragmas per the `SqliteCodebaseIndex` contract), and `BufferedAuditLogger` — bounded channel, batched background flush, per-entry durability confirmation for the change trail (`TaskCompletionSource` set by the flusher, bounded by `FlushTimeout`), fire-and-forget for the access trail, fail-open everywhere. Change entries are never silently dropped: a full channel delays the caller within the bound and never fabricates durability. Retention: `AuditRetentionPolicy` (change 365 days / access 14 days) and `AuditMaintenanceJob` — one shared `AuditDayFiles` reader (raw + gzip), rollups that fold every closed day into `rollups/<date>.jsonl` (min/median/max duration per category/action/actor/outcome group, merged per (trail, date) so partial runs neither duplicate nor clobber across trails), raw deletion gated on expiry. Timestamps are logger-normalized to UTC; the label vocabulary is single-source (`AuditLabels`) across JSONL, rollups, and the index. Tests: 21 focused suites' worth of new xUnit coverage (channel overfill durability, field-by-field enrichment, UTC normalization, options guards, gzip rotation round-trip, rebuild-from-JSONL, cross-trail rollup merge, legacy-label tolerance), RED-first per behavioral fix; whole `Eling.Core.Tests` project 353/353, api-layer convention suite 9/9. Known deferred by design: the §14 audit-degraded signal, the job's daily scheduling (Phase 5 wiring), and all hook/API/UI phases.
- **MCP tool policy enforcement**: The per-user tool enablement policy (`tools-policy.json`) is now enforced at the MCP boundary — `ListToolsFilter` strips disabled tools from `tools/list`, `CallToolFilter` short-circuits calls to disabled tools with the standard `tool_disabled` error before the handler runs. Both filters resolve the store per request, so a policy toggle takes effect on the next request without restarting the host, and a missing store fails open so an unresolvable dependency never bricks tool calls.
- **Chat tool `tools_policy`**: List, enable, disable, and reset for individual tools or whole groups from chat, with protected tools rejected and every mutation persisted through the store.

### Changed
- **Recall overflow summarized, not skipped (`recallSummary`)**: `recallLimit` used to end the story — the search asked for at most N hits, so relevant items ranked N+1 and beyond never left the FTS layer. The recall service now takes a second, wider fetch (only when the cap is actually filled, so the interleave guarantee for the top N is unchanged), and the hits beyond the limit are summarized into a new `recallSummary` response field: `{ itemCount, summarizedCount, source, paragraphs[] }` — multi-paragraph by design, so a long record is split across paragraphs instead of crammed into one. The digest is written by the semantic judge when configured (`ProviderSemanticJudge` now also implements a new `ISemanticSummarizer`, sharing the same per-user config store, Polly pipeline, and circuit breaker; `RecallSummaryPrompt` is the pure, unit-tested prompt) and degrades to a deterministic digest (`RecallSummaryFallback`, bounded at ten items / five paragraphs / ~180 chars per fragment) when the judge is unconfigured, times out, fails, or returns nothing usable — with the cause recorded in `note`, mirroring the save pipeline's `judge-failed: ...; fell back` posture. `source` tells the two apart (`judge` vs `heuristic`); `summarizeOverflow: false` skips the summary for minimum latency. The MCP instructions, both tool descriptions/schemas, `docs/recall-architecture.md` §6, and `docs/semantic-judge-architecture.md` §6 document the contract.
- **Standing baseline in every `memory_recall` response**: Recall no longer depends on the caller choosing good topics to stay consistent. Every response now carries `standingMemories` — a topic-independent baseline of active standing rules/preferences, standing decisions, and lessons, ordered current-project first then most recently updated, capped at five, with ids already present in the topic hits excluded. It is derived from the same active-memory enumeration that already fed `recentMemories`, so there is no extra query. Entries are marked `matchedVia: ["standing"]` / `queryMode: "standing-baseline"` so clients can tell them from search hits. The MCP server instructions, the tool description, and `docs/recall-architecture.md` describe it as the server-enforced consistency spine: a narrow topic call still surfaces the standing spine.
- **Session-start recall is broad by design**: The MCP server instructions, the `memory_recall` tool description, the builtin-agent wrapper (`MemoryRecallAgentTool` description + JSON schema), and the in-app agent system prompt (`AgentTurnService`) now mandate a BROAD first-turn topic set — the opening message's topics plus standing rules and preferences, standing decisions, lessons and known gotchas, workflow/repo conventions, and recently touched work — instead of anchoring solely on the opening message's subject. The instruction text shows the exact call shape (`context: { topics: [...] }`, with the top-level `topics` alias noted) and requires a `stats.recallCount` self-check after the call: zero means mis-shaped or no match, so re-issue before treating recall as done (bounded retries). `docs/recall-architecture.md` corrects its call-shape example — which had shown the flat shape that silently failed — and gains two strategic rules: session-start breadth and the zero-result self-check.
- **Codebase page scope panel & docked file viewer** (dashboard): Wide screens (xl+) replace the scope dropdown with an always-visible workspace list panel — click a row for a single scope, checkboxes for an explicit multi-root set — while narrow screens keep the Select. The URL query is the selection's source of truth (repeated project params, plus `file`/`fileRoot` for the open viewer) through one shared writer, so reload, back/forward and shared links restore the same state and a scope change never drops the open file. The file viewer docks as a right-hand column at xl+ with the list column fixed and the viewer filling the rest; below xl the centered modal remains. Selection model and URL builders live in `scope.ts`; breakpoints come from `lib/constants.ts`.
- **Single binary `eling-backend`**: Merge `Eling.Host` + `Eling.Dashboard` + `Eling.Mcp` + `Eling.Application` → `Eling.Core` + `Eling.Backend` (`Microsoft.NET.Sdk.Web`). One process serves MCP (stdio) + REST (4317/4417) + UI. Removes `SpawnDashboard`, `DashboardCoordinator`, `DashboardLauncher`, `DashboardPaths` cross-process coordination.
- **Backend layout**: `Eling.Core` now owns Memory, Storage, Serialization, Intention, Scope, Runtime, MemoryRecall (flat `Eling.Core` namespace). `Eling.Backend` owns `Bootstrap/`, `Mcp/Tools/`, `Endpoints/`, `Dtos/` (single `Dtos/` folder, 13 DTOs).
- **DTO consolidation**: `Eling.Backend/Dtos/` + `Eling.Backend/Mcp/Dtos/` → single `Eling.Backend/Dtos/` (namespace `Eling.Backend.Dtos`). `Mcp/Tools` split: `MemoryWriteTool`, `MemoryReadTool`, `MemoryIndexTool`, `MemoryPromoteTool`, `MemoryRecallTool` (one logical tool per file).
- **Port ownership**: `RuntimeRegistry.Alive()` now filters `UserScope` sentinel. Frontend `memories/page.tsx` shows full ULID (`break-all`) instead of `6…4` truncation.
- **Dev servers**: Kestrel listens on `127.0.0.1` + `::1` (dual stack) so `localhost:4427` and `127.0.0.1:4427` both work. Next.js dev: `next dev -H 0.0.0.0 -p 4427`. `Eling.Backend` probes port before bind — if peer owns 4317/4417, skips Kestrel and runs MCP-only.
- **Scripts**: `package.json` `dev:backend` → `Eling.Backend.csproj`, `opencode.json` `eling_dev` → `watch --project Eling.Backend`, `scripts/validate-eling.ps1` + `test-single-mode.ps1` updated to `eling-backend.exe`, workflows `release.yml`/`pre-release.yml` publish single `Eling.Backend`.
- **MCP tool `session_start` → `memory_recall`**: renamed the on-demand context-hydration tool so the name reflects what it actually does (recall memories) rather than when it was historically called. The MCP `Name` is now `memory_recall`. Folder `Eling.Core/SessionStart/` is renamed to `Eling.Core/MemoryRecall/`; `ISessionStartService` → `IMemoryRecallService`; DTOs `SessionStart*` → `MemoryRecall*`. Bug fix: the previous implementation dropped the `topics` input and always returned `recallMemories: []`, and `recentLimit` was hard-coded to `Take(5)` regardless of the parameter; the new service actually performs `ScopedMemoryService.SearchAsync(topics, scope, recallLimit)` and respects `recentLimit`. New stats fields `recallCount` / `recentCount` surface the actual returned counts.
- **Workspace catalogue self-cleans rows whose folder is gone**: `JsonWorkspaceRegistry` treated every row as permanent — once a folder was registered, its `agent-workspaces.json` row outlived not just the process that wrote it but the folder itself, so a deleted project or a cleaned-up temp dir left a listing entry pointing at nothing forever (observed live: 12 of 39 rows in the real catalogue pointed at missing folders — 9 `eling-lifecycle-*` and 3 `eling-smoke-*`, all test leftovers). `IWorkspacesRegistry.DeleteMissingRootsAsync` drops rows whose workspace folder no longer exists on disk and reports how many were removed, under the same cross-process mutex gate as every other mutation, rewriting the file only when something was actually dropped, and never throwing — a failed prune costs a few dead rows until the next pass. `RuntimeRegistry.Sweep` invokes it after every sweep (default 15s), outside the runtime lock — the store serializes its own file access, so holding the lock across file IO would only stall every other caller — with an interlocked overlap guard so a slow prune is never piled on by the next tick, and an information log recording how many rows a pass removed. Rows whose folder still exists are kept even when their process is dead, which is the catalogue's whole point (a codebase index stays readable after its owner exits); the sweep comment that used to say "nothing is written to the catalogue here" now distinguishes the two cases: a dead process keeps its row, a dead folder loses it.
- **Audit trail design amended post-lock (2026-10-14)**: The locked v1 audit-trail design and its Phase 1 plan were reconciled against the current codebase. The audit `scope` field gains `project-local` (the post-flip `memory_save` default); the store root resolves through `ElingPaths.ResolveAuditDir` so the `ELING_DATA_DIR` override isolates test scopes; the MCP actor name is supplied per host via environment variable (`mcp` fallback) instead of the nonexistent `ELING_MCP_SERVER_NAME`; memory-audit scope is read from `ScopedMemoryService`/`MemoryReference` rather than a `MemoryService` constructor descriptor; filesystem hooks target `FileSystemService` (the single choke point behind MCP `FileSystemTools` and the builtin agent's file tools); `SqliteAuditIndex` adopts the repo's WAL / `busy_timeout` / `foreign_keys` pragma contract; and change-trail durability becomes a per-entry flush confirmation (a `TaskCompletionSource` the flusher sets when the batch lands, bounded by `FlushTimeout`) instead of a bounded wait that could not distinguish written from pending. Phase 1 Tasks 0, 6, and 7 patched in place; Phases 2–5 unchanged.
- **Audit trail tool-surface scope amended (2026-10-14, amendment B)**: A scope review corrected the audit-trail action tables against the real tool surface and added coverage the September spec lacked. Action names now mirror actual MCP tool names one-to-one — the September tables named tools that never shipped (`memory_read`, `memory_copy`, `memory_move`, the `fs_*` family); the filesystem domain now reads `file_write`/`file_edit`/`file_append`/`file_delete`/`file_move`/`file_copy`/`directory_*` with access actions `file_read`/`file_read_any`/`file_search`/`glob`/`directory_list`/`path_test`/`workspace_root`, and the memory domain gains `memory_project_scope_policy` and `memory_rebuild_index` (`memory_save`'s `SaveAction` distinguishes create from smart-save update). Two new domains bring the total to five: `codebase` (explicit `codebase_index` invocations only — watcher-driven incremental refreshes stay excluded under the §12 self-noise rule — plus `codebase_search`/`codebase_status` access) and `tools` (`tools_policy` mutations as change entries with the tool/group in the target, `denied` outcome for protected tools, and `list` as an access action; neither domain's change actions carry a state snapshot, keeping the before/after snapshot memory-specific). §5 gains a fourth actor family `agent:<name>` (source `agent`) — the builtin agent turn opens the ambient actor scope so agent-driven service operations stop masquerading as `dashboard`/`system`. The amendment also records that six shipped filesystem tool descriptions already promise "(audited via telemetry)" — a promise awaiting Phase 2 — and closes the raw-payload question as an explicit non-goal: the unit of audit remains the domain operation, not the transport call. No engine or Phase 1 change: actions are open strings, so this lands with the Phase 2/3 hook plans.
- **Audit trail UI naming (2026-10-14)**: The Phase 4 dashboard route and view are named `audit-trail` (`/dashboard/audit-trail`) — not "Activity Log" as §10/§11/§16/§17 originally said. No frontend file carries either name yet (Phase 4 is unstarted), so this is a design-only rename with zero code impact. The superseded 2026-08-29 documents keep their old naming; they are historical records.

- **`memory_save` default scope flips to `project-local`** (user decision 2026-10-14): `MemoryScopePolicy` (blank + the `auto` alias), the `memory_save` MCP tool, and the builtin-agent wrapper all default to `project-local` (machine-only, never committed) instead of `project`. The `ServerInstructions` scope rules, both tool descriptions/schemas, and `docs/using-eling.md` encode the same order: `global` for knowledge that holds in a different, unrelated project; `project-local` for anything bound to this repo; `project` (committed, shared via git) only on explicit request. Agents kept drifting memories into the commit tier — the tool default and its description both pushed that way — and in this public repo `.eling/memories/` is never committed anyway, so project scope shared nothing while local-first removes the accidental-commit vector. Consequences: the `init-required` consent nudge now fires on explicit `scope=project` saves rather than default saves, and ancestor targeting (the `project=` parameter) requires explicit `scope=project` — combining it with the default throws `ArgumentException`, sharing being explicit at both layers. `memory_delete` defaults are unchanged, dashboard create keeps its explicit `tier` parameter, and `auto` is no longer advertised in schemas but remains accepted as an alias of the default. Amends the default locked in `docs/superpowers/specs/2026-10-09-local-only-project-memory-design.md` §5/§6/§9 (amendment block appended there).
- **Memory content shape joins the agent contract**: A new `Memory Content Shape (HARD RULE)` section in the MCP server instructions, plus the `memory_save` tool description (MCP and builtin-agent wrapper, including its JSON schema), now require a memory's content to BE the decision, rule, lesson, or fact — standalone durable guidance a future session can apply without knowing the conversation that produced it. Exchange narration, diary framing ('earlier today', 'in this session'), advice that only makes sense inside the chat, and quoting the user are all forbidden; only the decision, its rationale, its scope, and its verification survive. The rule had lived only in Eling memory, where intermittent recall left it unenforced — the handshake text reaches every client even when recall is skipped, and the ServerInstructions contract test pins the new section.

### Fixed
- **`memory_maintenance` could not see the corpus it claims to scan**: `MemoryMaintenanceService.RunAsync` iterated the requested scopes but every iteration called `ListAllAsync()` on the same head `IMemoryService`, so each scope's "scan" listed the head memories while findings carried the requested scope as a cosmetic label — a merged dry-run over a 235-memory corpus reported `memoriesScanned: 2` with zero findings, making the 0-duplicate verdict meaningless. The service now depends on `IScopedMemoryService` and resolves the real storage per scope (`LocalService` / `ProjectService` / `GlobalService`): `Merged` scans project-local + project + global, an unwired local shard or an uninitialized project scope contributes an empty scan (never another scope's list), and merge/delete mutations resolve the service from the finding's own scope instead of the head. `MaintenanceScope` gains `ProjectLocal`, so the tool's already-documented `project-local` value stops silently falling through to `Merged` — the scope switch mapped every unrecognized string, including `project-local`, to merged. Verified live after the fix: merged scans the real corpus (232 scanned; global 182; project-local 49). Known limits, recorded and unchanged: dedup detects exact normalized-content matches only; merge compares same-type pairs by content Jaccard only; `DetectReconcileCandidates` remains an empty stub; `Project` scans the chain head level only, not ancestor project scopes. Locked by five new cases in `MemoryMaintenanceServiceTests` (per-scope scanning, truthful labels, scope isolation; full Core suite 341/341 green).
- **Dashboard sidebar active menu highlight**: `NavMain` now reads the current URL with `usePathname()` and passes `isActive` to `SidebarMenuButton` and `SidebarMenuSubButton`, matching exact routes (e.g. `/dashboard`), sub-routes (e.g. `/dashboard/workspaces`), and related actions (e.g. `/dashboard/create` activating Memories). Removed hardcoded `isActive: true` from static `navMain` items in `AppSidebar`.
- **Codebase page self-heals when the backend returns**: the codebase page shows one error banner for both loaders (status and runtime rows), and until now the only way back was a manual Status press, so a backend that went down and came back left the page dead with nothing prompting recovery. While either loader's error is set, a 5-second interval now re-checks the status endpoint and silently re-loads the workspace rows; each loader clears its own error on the first HTTP 200, which tears the interval down, so healthy browsing never polls (the page keeps its refresh-only-on-events design) and a failing probe never flashes the banner or drops the last good rows while the failure persists.
- **`memory_save` ancestor-targeting contract documented**: since the default scope flipped to `project-local` (commit a3286f3), passing the `project` parameter without an explicit `scope=\"project\"` throws `ArgumentException` — the old text only said ancestor targeting "requires the current workspace to already have its own .eling scope". The tool description and the `project` parameter description now state the explicit-scope requirement and name the failing combinations (`global`, and the `project-local` default). Text-only: no behavior change.
- **MCP instruction text now matches the post-flip save behavior**: five fixes across six text surfaces, all of which still described the pre-2026-10-14 world. `memory_project_scope_policy`'s description claimed a `disabled` policy routes writes to `global` — it routes project-bound saves to `project-local` (machine-only, never committed) and has since the flip. The server instructions claimed an explicit `scope=project` save in a workspace without a scope returns init-required — true only for ancestor-scope workspaces; in an empty chain (no `.eling` anywhere up) the save lands in project-local with a note offering `memory_init_project` only when sharing is wanted. And "Local project memory requires explicit user consent before initializing" read as if project-local saves needed `.eling` — consent gates only `.eling`, the committed tier. `memory_project_status` now states that `initialized` describes the committed tier only, and the `memory_get`/`memory_delete` scope descriptions warn that saves default to `project-local` while get/delete defaults stay `project`, so a default lookup or delete by ULID can miss project-local memories. Text-only: no behavior, defaults, or code paths changed.
- **Workspace catalogue no longer auto-registers `.eling` ancestors**: `RuntimeRegistry.Register` recorded not just the folder the runtime runs in, but every level of its `.eling` scope chain, so a `.eling` initialized at an ancestor (e.g. a shared parent folder) was quietly added to the workspace catalogue every time any child workspace registered — it then showed up in the dashboard's workspace and codebase lists as a remembered workspace nobody ever opened, and only a deleted folder or a manual dashboard removal cleared it. The catalogue's own contract (`RegisteredWorkspace`: "the directory the backend runs in — the codebase index root, never a `.eling` ancestor") was never enforced on this path. `Register` now mirrors exactly one row — the registering workspace, with the head scope stored as a field rather than a second row — and `RecordChainWorkspaces` is gone. Memory access is unaffected: the dashboard's scope picker resolves the `.eling` chain from disk on every request (`ProjectScopeCatalog`, covered by `ListsOwnScopeAndAncestorsFromDiskWithNoRegistry`), and MCP recall fans out over chain levels, so ancestor scopes never depended on the catalogue. Rows written by earlier builds remain until their folder is deleted or removed from the dashboard. Locked by `RuntimeRegistryWorkspaceRecordingTests`.
- **`memory_recall` silently dropped a top-level `topics` argument**: the tool only read `context.topics`, so any caller passing the intuitive flat shape got zero topic-relevant recalls with no error while the call still looked successful — and neither the instruction text nor `docs/recall-architecture.md` ever showed the nested shape, making the failure invisible (observed live 2026-10-14: flat call → `recallCount: 0`; nested call → 10 hits). The tool now accepts a top-level `topics` alias (when non-empty it replaces `context.topics`), and the builtin-agent wrapper parses the same alias from its arguments JSON.
- **Tool policy coherence across processes**: `ToolPolicyStore` loaded `tools-policy.json` once at construction and kept a per-process snapshot, so a `tools_policy` enable made through one process stayed invisible to the others sharing that file, and a later dashboard toggle re-committed from the stale snapshot and silently reverted the chat-driven change (observed live: the dashboard API reported `file_search` disabled while the file and both MCP hosts reported it enabled). `RefreshIfStale` now re-reads the file whenever its mtime+length stamp changed, from every read path and before every mutation, and re-stamps after a successful write; corrupt or deleted files keep the last good snapshot.
- **Peer memory mutations reach the dashboard owner**: A peer eling serves no SSE, so its in-process `MemoryChangeBroadcaster` had zero subscribers and a memory saved from another workspace left the dashboard silently stale. `IMemoryChangeNotifier` now resolves to `HttpCoordinatorMemoryChangeNotifier`, which POSTs to the owner's `/api/coordinator/notify-change`; the endpoint takes an optional `reason` body and relays it as the SSE topic instead of collapsing every notification to one.
- **Test determinism in `ProjectContext` discovery**: Tests previously mutated process-global state (`Directory.SetCurrentDirectory` in the constructor, restored in `Dispose`), which could crash parallel test collections mid-run when a fixture's temp directory was deleted. `Discover` now takes the start directory explicitly, defaulting to the process working directory; production behavior is unchanged.
- Frontend ID truncation and scope selector showing `UserScope` as project.
- `pnpm build` path for `BuildDashboard` msbuild target (relative `MSBuildThisFileDirectory`).
- `Eling.Core` `Intention` namespace collision (`Intention` class vs namespace) by keeping flat `Eling.Core` namespace.

### Changed
- **Recall overflow summarized, not skipped (`recallSummary`)**: `recallLimit` used to end the story — the search asked for at most N hits, so relevant items ranked N+1 and beyond never left the FTS layer. The recall service now takes a second, wider fetch (only when the cap is actually filled, so the interleave guarantee for the top N is unchanged), and the hits beyond the limit are summarized into a new `recallSummary` response field: `{ itemCount, summarizedCount, source, paragraphs[] }` — multi-paragraph by design, so a long record is split across paragraphs instead of crammed into one. The digest is written by the semantic judge when configured (`ProviderSemanticJudge` now also implements a new `ISemanticSummarizer`, sharing the same per-user config store, Polly pipeline, and circuit breaker; `RecallSummaryPrompt` is the pure, unit-tested prompt) and degrades to a deterministic digest (`RecallSummaryFallback`, bounded at ten items / five paragraphs / ~180 chars per fragment) when the judge is unconfigured, times out, fails, or returns nothing usable — with the cause recorded in `note`, mirroring the save pipeline's `judge-failed: ...; fell back` posture. `source` tells the two apart (`judge` vs `heuristic`); `summarizeOverflow: false` skips the summary for minimum latency. The MCP instructions, both tool descriptions/schemas, `docs/recall-architecture.md` §6, and `docs/semantic-judge-architecture.md` §6 document the contract.
- **Standing baseline in every `memory_recall` response**: Recall no longer depends on the caller choosing good topics to stay consistent. Every response now carries `standingMemories` — a topic-independent baseline of active standing rules/preferences, standing decisions, and lessons, ordered current-project first then most recently updated, capped at five, with ids already present in the topic hits excluded. It is derived from the same active-memory enumeration that already fed `recentMemories`, so there is no extra query. Entries are marked `matchedVia: ["standing"]` / `queryMode: "standing-baseline"` so clients can tell them from search hits. The MCP server instructions, the tool description, and `docs/recall-architecture.md` describe it as the server-enforced consistency spine: a narrow topic call still surfaces the standing spine.
- **Session-start recall is broad by design**: The MCP server instructions, the `memory_recall` tool description, the builtin-agent wrapper (`MemoryRecallAgentTool` description + JSON schema), and the in-app agent system prompt (`AgentTurnService`) now mandate a BROAD first-turn topic set — the opening message's topics plus standing rules and preferences, standing decisions, lessons and known gotchas, workflow/repo conventions, and recently touched work — instead of anchoring solely on the opening message's subject. The instruction text shows the exact call shape (`context: { topics: [...] }`, with the top-level `topics` alias noted) and requires a `stats.recallCount` self-check after the call: zero means mis-shaped or no match, so re-issue before treating recall as done (bounded retries). `docs/recall-architecture.md` corrects its call-shape example — which had shown the flat shape that silently failed — and gains two strategic rules: session-start breadth and the zero-result self-check.

- **Workspace catalogue self-cleans rows whose folder is gone**: `JsonWorkspaceRegistry` treated every row as permanent — once a folder was registered, its `agent-workspaces.json` row outlived not just the process that wrote it but the folder itself, so a deleted project or a cleaned-up temp dir left a listing entry pointing at nothing forever (observed live: 12 of 39 rows in the real catalogue pointed at missing folders — 9 `eling-lifecycle-*` and 3 `eling-smoke-*`, all test leftovers). `IWorkspacesRegistry.DeleteMissingRootsAsync` drops rows whose workspace folder no longer exists on disk and reports how many were removed, under the same cross-process mutex gate as every other mutation, rewriting the file only when something was actually dropped, and never throwing — a failed prune costs a few dead rows until the next pass. `RuntimeRegistry.Sweep` invokes it after every sweep (default 15s), outside the runtime lock — the store serializes its own file access, so holding the lock across file IO would only stall every other caller — with an interlocked overlap guard so a slow prune is never piled on by the next tick, and an information log recording how many rows a pass removed. Rows whose folder still exists are kept even when their process is dead, which is the catalogue's whole point (a codebase index stays readable after its owner exits); the sweep comment that used to say "nothing is written to the catalogue here" now distinguishes the two cases: a dead process keeps its row, a dead folder loses it.
